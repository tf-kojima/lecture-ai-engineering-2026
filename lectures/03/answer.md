# 第3回 解答

## 演習

- 第1回（素のLLM）とエージェントの回答の違い：
  同じ質問「第2回の内容から確認問題を1問出して」で比べた。
  第1回の `app.ask`（素のLLM）は講座の情報を何も持たないため、「第2回」が何を指すか分からないと答え、
  テーマや資料を教えてほしいと聞き返してきた（問題は作れなかったが、でっち上げもしなかった）。
  エージェントは `make_quiz({'lecture': 2})` を呼んで用語集から第2回の用語「量子化」を取り出し、
  それをもとにヒント付きの問題を出した。
  モデル自体は同じ gemini-3.5-flash-lite なので、差を生んだのはモデルの賢さではなく、
  ツールを通じて講座のデータにアクセスできるかどうかだと分かった。

- `--trace` で見えたツール呼び出し（ツール名と引数）：
  「第2回の内容から確認問題を1問出して」では、`[tool call] make_quiz({'lecture': 2})` が1回だけ呼ばれた。
  モデルは「第2回」という文言から引数 `lecture=2`（integer）を正しく組み立てており、
  `search_glossary` や `get_lecture_summary` は呼ばれなかった。
  ツールは `{"question": "「量子化」の意味は？", "answer": "モデルの重みを少ないビット数で表し…"}` を返した。

- 1つの質問での LLM 呼び出し回数（`requests`）：
  2回（`requests=2, tool_calls=1`）。
  1回目でモデルが make_quiz を呼ぶと判断し、2回目でツールの返り値を受け取って出題文を作った。
  素の LLM（1回）より多い。

- 追加したツールと、docstring に書いた説明：
  `app/tools.py` に `make_quiz(lecture: int) -> str` を追加し、`app/agent.py` で `agent.tool_plain(tools.make_quiz)` と登録した。
  - 処理：`load_glossary()` から `lecture` が一致する用語を集め、`random.choice` で1つ選び、
    `{"question": "「用語」の意味は？", "answer": 定義}` を `json.dumps(..., ensure_ascii=False)` で返す
  - 用語が無い回（第0回・第5回など）では、例外にせず「用語がある回」の一覧を返す（pytest のダミー引数 `lecture=0` 対策）
  - docstring：「指定した回の用語から１つを選び、確認問題と答えを返す。『第2回の確認問題を出して』のように、復習用の問題を求められたときに使う。」
  - 確認：`--list-tools` に3つ目のツールとして表示され、`uv run pytest -q` は 15 passed。

## 宿題

- 取り組んだレベル：基礎
- やったこと：
  演習の make_quiz で、指示しなくてもモデルが答え（answer）を伏せて出題したことに注目し、
  「答えも示す」ように指示を変えたら答えを出すのかを、1か所ずつ変えて比べた。
  質問はすべて「第2回の内容から確認問題を1問出して」で、--trace 付きで実行した。
  1. make_quiz の docstring に「返り値の question と answer は、両方そのまま利用者に示すこと。」を追加
  2. 1 に加えて、INSTRUCTIONS から「宿題の答えそのものは書かず、考え方のヒントで導く。」を削除
     （1 で伏せた原因がこの行だと考えたため）
  変更が反映されていることは --list-tools と git diff で確認した。
- 結果：
  | 条件 | ツール呼び出し | requests | 答えを出したか |
  |---|---|---|---|
  | 変更前 | make_quiz({'lecture': 2}) | 2 | 伏せた（ヒント付きで出題） |
  | 1. docstring に「両方示す」 | make_quiz({'lecture': 2}) | 2 | 伏せた（「答えを知りたければ聞いて」） |
  | 2. ＋「宿題の答えは書かず…」削除 | make_quiz({'lecture': 2}) | 2 | 伏せた（「答えを教えて」と聞くよう促した） |
  ツールの呼ばれ方（ツール名・引数・回数）はどの条件でも変わらず、回答の出し方も変わらなかった。
- 気づき・疑問：
  - docstring の指示は無視されたわけではなく、モデルには届いていた（--list-tools で確認）。
    それでも従わなかったので、「確認問題を出すなら答えは伏せる」というモデル自体の傾向が強いと考えられる。
  - 「宿題の答えは書かない」の行が原因という仮説は外れた。
  - docstring は「ツールをいつ・どの引数で呼ぶか」の判断には効く（演習で lecture=2 を正しく渡した）が、
    「ツールの結果をどう見せるか」には効きにくいのではないか。
  - input_tokens は返り値（ランダムに選ばれる用語の定義の長さ）で変わるため、条件の比較には使えなかった。
  - 疑問：同じ指示を docstring ではなく INSTRUCTIONS に書けば従うのか。出力は確率的なので、回数を増やすと結果は変わるか。
